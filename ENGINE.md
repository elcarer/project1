# Документация движка (engine)

ECS-движок 2D-игры на **PixiJS 8.19** без сборщика и зависимостей (кроме самой PixiJS, подключённой локально).
Дата последнего обновления: 2026-09-13 (dualgrid: слой объектов + вкладки в редакторе). Бэкап кода до первого рефакторинга: `../engine-backup-before-refactor/`.

## Как запустить

ES-модули не работают с `file://` — нужен любой статический HTTP-сервер из папки `engine/`:

```bash
python nocache-server.py   # отдаёт Cache-Control: no-cache (рекомендуется для разработки)
# открыть http://127.0.0.1:8137/
```

⚠️ Обычный `python -m http.server` не шлёт заголовков кэширования — браузер может отдавать
модули из эвристического кэша, не обращаясь к серверу (симптом: правки не применяются).
Импорты модулей содержат `?v=2` — при «залипании» кэша поднимите версию в импортах.

Исключение — инструменты-редакторы **editor.html** и **dualgrid_editor.html**: их скрипты
подключены обычными `<script>`-тегами (глобали), поэтому они работают и по двойному клику
с `file://`, без сервера.

**Принцип разделения:** `engine.js` не содержит ни одного конкретного объекта — только
переиспользуемые механизмы. Всё, что относится к конкретной игре (какие текстуры, какие
типы юнитов, сколько и кого спавнить) — в `game.js`. Модули опциональны: ядро не знает
о них, каждый модуль подключается импортом и фабрикой в `game.js`.

## Ядро: ECS-подход

- **Сущность (Entity)** — просто числовой ID (`0..99999`). Никаких методов и полей.
- **Компонент (Component)** — чистые данные без логики.
- **Система (System)** — вся логика; работает только с группами-запросами.

### 1. Данные компонентов

Два хранилища (SoA — structure of arrays):

| Хранилище | Что лежит | Доступ |
|---|---|---|
| `COMPONENTS` | числовые данные в **типизированных массивах** | `COMPONENTS.positionX[id]` — O(1), кэш-дружелюбно |
| `DATA` | ссылочные данные: спрайты и т.п. | `DATA.spriteMap[id]` |

Компоненты ядра: `positionX/Y`, `velocityX/Y`, `configId`, `radius`, `gridCellId`,
анимационные `currentFrame/totalFrames/animationSpeed/animationTime` (кадры считает сам
AnimatedSprite, `animationSpeed` — маркер группы «animated»).

**Динамическая регистрация:** `ECS.registerComponent(name, type, length)` — модуль может
добавить свой компонент без правки ядра (так делает `health.js`: `hp` = бит 12, `maxHp` = бит 13).
Повторная регистрация идемпотентна. **Лимит: 32 компонента** (Uint32Array-маска), свободные
биты ищутся автоматически, при исчерпании — warning и `null`.

### 2. Группы-запросы (queries)

`ECS.createQuery(world, имя, [компоненты])` собирает битовую маску требований. Система
перебирает только плотный массив `world.queries.<имя>.entities`; попадание/удаление —
автоматически через `updateQueries` при изменении маски, удаление O(1) swap-and-pop.

Группы ядра: `movable`, `renderable`, `aliveUnits`, `animated`, `physics`; модуль health
добавляет `vulnerable` (зарегистрирован, используется игрой по необходимости).

### 3. Игровой цикл и системы модулей

```
app.ticker (каждый кадр):
  1. movementSystem     — movable:   позиция += скорость × dt (нормализация к 60 FPS),
                                     отскок от setWorldBounds() или краёв экрана
  2. spatialGridSystem  — physics:   очистка и перестройка пространственной сетки
  3. collisionSystem    — physics:   столкновения кругов, расталкивание + упругий отскок
  4. animationSystem    — animated:  sprite.update(ticker); скрытые вне вида камеры
                                     (visible=false от рендера прошлого кадра) пропускаются
  5. renderSystem       — renderable: спрайт.x/y = позиция + CULLING: всё вне вида камеры
                                     получает visible=false (PixiJS пропускает его целиком)
  6. СИСТЕМЫ МОДУЛЕЙ    — всё, что зарегистрировано через engine.addSystem(fn)
                          (камера, fx, hud, scenes, debug — в порядке подключения)
```

`addSystem(fn)` — точка расширения: ядро не знает числе систем модулей, вызывает каждый
кадр после своих. Скорости задаются в «пикселях за кадр при 60 FPS» — на 144 Гц движение
то же самое (проверено: 240 px/с при 143 FPS).

### 4. Сцена и контейнеры (PixiJS)

```
app.stage
├── worldContainer      ← МИРОВЫЕ координаты: им управляет камера (позиция/масштаб/тряска)
│   ├── частицы FX, визуализация отладки (сетка/хитбоксы)
│   ├── particleContainer (анимированные спрайты)
│   └── статические спрайты юнитов
├── hud.container       ← ЭКРАННЫЕ координаты: HUD, не зависит от камеры
├── debug.overlay       ← оверлей статистики
└── canvas
```

- **Пулы спрайтов.** Спрайты не создаются/не уничтожаются в рантайме: при смерти сущности
  спрайт прячется и возвращается в пул своего типа. Пулы **раздельные**:
  `STATIC_SPRITE_POOLS[typeIndex]` для `PIXI.Sprite` и `ANIMATED_SPRITE_POOLS[typeIndex]`
  для `PIXI.AnimatedSprite`. Прочие объекты (частицы, тексты FX) — через дженерик-пул `pool.js`.
- **Анимация.** `PIXI.AnimatedSprite(textures, false)`: 1 объект сцены на юнита,
  `autoUpdate=false` — кадрами управляет `animationSystem`.
  ⚠️ **Нюанс API:** в PixiJS 8.19 `AnimatedSprite.update(t)` ждёт **объект тикера** (читает
  `t.deltaTime`). Передача числа даёт NaN → спрайт исчезает из рендера.
- **Текстуры.** Программный атлас (`createProgrammaticSpritesheet`), загрузка спрайтшита
  (`loadSpritesheetFromImage` в ядре, `assets.loadSpritesheet` в модуле — с кэшем и прогрессом).
  Конфиг юнита поддерживает `spriteScale` (масштаб спрайта, применяется фабриками пула при
  создании и переиспользовании) — для уменьшения готового арта без перерисовки/нарезки.
- **Рендерер.** `app.init({ preference: "webgpu" })`: при недоступности WebGPU PixiJS сам
  откатывается на WebGL. Активный рендерер — `app.renderer.name` (выводится в консоль игры).

### 5. Пространственная сетка (SpatialHashGrid)

ДВУХУРОВНЕВАЯ сетка поверх `Map`. **Точный уровень** (16px, `cellSize` — адаптивный:
`max(16, 2×макс.радиус конфигов)`) хранит ID сущностей; каждый кадр `clear()` возвращает
массивы ячеек в пул `freeArrays` → `insert()` по `getCellKey(x,y)`. Ключ уникален для любых
координат (схема `(col+32768)*65536 + (row+32768)`) — коллизий ключей нет даже при
отрицательных координатах; обратный разбор — `getCellCoords(key)`.

**Грубый уровень** (`coarseSize: 64`, битовая карта занятости 1024×1024 блоков): при
переборе соседей позволяет пропустить точный Map.get, если весь блок 4×4 ячеек пуст
(`useCoarse`). По замерам ВЫКЛЮЧЕН по умолчанию: на плотной толпе все блоки заняты и
фильтр даёт +10% кадра, в разреженном — нейтрален; выигрыш возможен лишь при очень
низкой заполненности блоков. Оставлен как диагностическая опция.

`collisionSystem` обходит ЯЧЕЙКИ, а не сущности: для каждой ячейки берутся пары внутри
неё и пары с четырьмя «передними» соседями (право, низ-лево, низ, низ-право) — каждая
пара сущностей проверяется ровно один раз, обращения к карте — 5 на ячейку. Дистанция —
сравнение квадратов; физика пары вынесена в `resolveCollision(a, b)`.
Уменьшение точной ячейки 32→16px при радиусах 5–6 сократило число проверяемых пар
в ~4 раза (плотность на ячейку): −15…20% времени кадра на нагруженной сцене.

### 6. События (шина `events`)

Ядро и модули генерируют, игра подписывается (`events.on`):

| Событие | Когда | payload |
|---|---|---|
| `unit:spawned` | spawnUnit / spawnAnimatedUnit | `{ id, configId }` |
| `unit:damaged` | health.damage() | `{ id, amount, hp }` |
| `unit:died` | health.kill() (до удаления — позиция ещё читается) | `{ id, configId }` |

Константы имён — `UNITS_EVENTS` в `data/units.js`.

## Генерация пола: Dual Grid System (modules/dualgrid.js + dualgrid_editor.html)

Автотайлинг по схеме Jess::Codes («двойная сетка»): тайл ложится не внутрь ячейки карты,
а на её угол — точку схождения 4 ячеек данных. Биты 4 ячеек (TL/TR/BL/BR) дают 2⁴ = 16
комбинаций — полный тайлсет всего 4×4 тайла (против 47 в классическом blob-автотайлинге),
а границы у местности получаются скруглёнными.

- **Карта** — `{ w, h, data }`, `data[y*w+x]` = 1 («фича»: земля/вода) или 0 (фон: трава).
  Слой пола занимает ровно `w*ts × h*ts` пикселей, тайл ячейки (i,j) выбирается по углам
  `D(i-1,j-1), D(i,j-1), D(i-1,j), D(i,j)`; за границами карты — значение `outside` (0).
- **build({texture, map, outside, hideBackground})** — собирает контейнер тайлов
  (нарезает тайлсет на 16 текстур, scaleMode «nearest»). **update(layer, map)** — подменяет
  карту с переиспользованием спрайтов (размер тот же) или пересобирает детей на месте.
- **Таблица углов TILE_CORNERS** — попиксельно выверена для `images/tiles/grass_dirt.png`
  и `grass_water.png` (раскладка у обоих одинаковая: тайл 6 — сплошная «фича», 12 — сплошной
  фон). Для чужого тайлсета 4×4: `detectLayout(текстура|изображение)` — автоопределение по
  цветам (фон = самый частый цвет, «фича» = самый далёкий от него из частых; окно 4×4 с
  отступом 2 у каждого угла голосует за ближайший эталон). Оба репозиторных тайлсета
  определяются точно (проверено в демо, «detectLayout 2/2»).
- **Наслаивание местностей** (река поверх пятен земли): верхний слой строится с
  `hideBackground: true` — его чисто-фоновые тайлы скрываются (у воды непрозрачная трава
  иначе закрасила бы нижний слой). Слои просто добавляются в один контейнер по порядку.
- **Подключение** — обычный `<script src="./scripts/engine/modules/dualgrid.js">` (как и
  pixi.min.js): модуль создаёт глобальную `createDualGrid()` и работает в том числе с
  `file://`. То же самое даёт `import "./dualgrid.js"` внутри ES-модуля (файл без
  `export` валиден как модуль, глобальная ставится как побочный эффект).
- **Редактор** `dualgrid_editor.html` (см. ниже) — рабочий инструмент для этих тайлсетов:
  генерация, рисование, сохранение/загрузка; старая демо-страница `dualgrid.html` удалена.

```js
const dual = createDualGrid();
const dirt  = dual.build({ texture: texGrassDirt,  map: dirtMap });
const water = dual.build({ texture: texGrassWater, map: waterMap, hideBackground: true });
worldContainer.addChild(dirt, water);
dual.update(dirt, newDirtMap);   // регенерация без пересоздания слоя
```

### Генератор и два формата файлов (по задумке геймдизайнера)

Два сценария, которые можно сочетать: **глобальную карту генерируют по манифесту**,
**локальные данжи отрисовывают из готового файла карты** (без генерации).

- **`generateMap({ w, h, seed, frequency, scatter })`** — процедурная карта `{w,h,data}`:
  fBm value-noise (3 октавы, детерминированный mulberry32; seed — число или строка).
  `frequency` — процент ячеек «фичи» (0..100), выдерживается **точно** порогом-квантилем;
  `scatter` — разброс: 0 — крупные материки (решётка 1.5 клетки), 100 — мелкие островки
  (до min(w,h)/2.2 клеток). Node-тесты: 30% → 30.01%; scatter 5 → 5–11 островков,
  scatter 95 → ~370 на 100×100.
- **Зазор между местностями (margin, default 3).** У тайлсетов без общего перехода
  (трава-земля ↔ трава-вода) стык «фича в фичу» рисуется прямыми срезами спрайтов.
  `mapFromManifest` при генерации отодвигает верхний слой от «фич» нижних слоёв с
  **другим** texture на `margin` клеток (дистанция Чебышёва ≥ margin+1, между ними
  остаётся полоса травы): `separateLayer(data, blockers, margin, w, h)` + `dilateMask`.
  Частота при этом выдерживается **после** раздвижки — если зазор съел часть слоя,
  входная частота детерминированно повышается до 8 итераций; если места всё равно нет
  (плотный нижний слой), слой получает максимум возможного (помогает меньший scatter
  или частота нижнего слоя). Слои с одинаковым texture считаются совместимыми и не
  раздвигаются. Node-тесты: дистанция после раздвижки ровно 4 при margin 3, дальние
  клетки уцелели, margin 0 ничего не трогает. Ловушка при стеке трёх и больше
  **разных** тайлсетов: blockers верхнего слоя — объединение всех нижних, и при
  плотностях по умолчанию (30%+25%) дилатация на 3 накрывает карту целиком — верхний
  слой молча остаётся пустым (компенсация частоты не спасает). Лечится уменьшением
  «зазора до нижних слоёв» у верхнего слоя до 0–1.
- **Привязка к фичам нижнего слоя (`on`, параметр слоя манифеста).** `on: "grass_dirt.png"`
  разрешает фичи слоя только внутри фич указанного нижнего слоя, с эрозией на 1 клетку
  (`erodeMask`) — переходные тайлы слоя лежат на его собственном фоне, а не на чужом.
  С привязанным слоем зазор не действует (их стык рисует его собственный тайлсет),
  от остальных нижних слоёв зазор сохраняется; «частота» считается по клеткам
  разрешённой зоны. Пример: снежные пятна (`snow_dirt.png`, фон земля) растут только
  на земляных пятнах `grass_dirt`, никогда на траве — стык снег↔земля гладкий из
  листа, а земля↔трава гладкая из `grass_dirt`. В редакторе — селект «поверх фич
  слоя» в панели активного слоя.
- **Манифест** (`format:"dualgrid-manifest"`): `{width, height, seed, layers:[{texture,
  frequency, scatter, outside, hideBackground, layout?, on?, png?}]}`. `makeManifest()` собирает
  с умолчаниями/проверкой; **`mapFromManifest(манифест, textures)`** генерирует и строит
  стек слоёв → `Promise<{root, layers, maps}>`. Сид слоя детерминирован:
  `hashSeed(`${seed}:${индекс}:${texture}`)` — движок и редактор дают идентичные карты
  (проверено двойной генерацией).
- **Файл карты** (`format:"dualgrid-map"`): `{width, height, layers:[{texture,
  data:[0/1…], outside, hideBackground, layout?}]}`. `makeMap()` собирает и валидирует;
  **`mapFromJSON(карта, textures)`** отрисовывает без генерации. Roundtrip проверен:
  сохранить → загрузить → данные совпадают побитово.
- **textures** — необязательный справочник `{ "имя.png": PIXI.Texture }` (ищется точное
  имя, затем базовое). Слой может нести `png: "data:image/png;base64,…"` — тогда файл
  самодостаточен (текстура грузится из самого JSON; редактор умеет вшивать их галкой
  «встроить PNG», загрузка из чистого реестра проверена).
- `layout` в файлах — таблица углов 16×4 (из `detectLayout`) для чужих тайлсетов;
  для репозиторных совпадает с `TILE_CORNERS` и может опускаться.

### Генератор мира: «🌍 Сгенерировать мир» (открытый мир для РПГ)

Классическая схема процедурной генерации миров: поля температуры/влажности
(широтный градиент + fBm-шум) задают вероятности местностей; точки интереса
расставляются разреженным поиском (упрощённый blue-noise / best-candidate).

- **`generateWorld({ w, h, seed })`** → `{ w, h, masks: { "grass_dirt.png", "grass_water.png",
  "snow_dirt.png", "sand_dirt.png" }, climate: { temp, moisture, snowZone, sandZone } }`.
  Температура `T = y/h + шум·0.36` → зоны `snowZone = clamp((0.40−T)/0.26)` и
  `sandZone = clamp((T−0.66)/0.26)`: волнистые границы поясов и карманы биомов в
  середине. Земляные пятна (субстрат снега/песка, привязка «on») гуще в поясах —
  0.14→0.76. Снег и песок — сумма ЗОННОЙ части (грубый шум, крупные поля) и
  РОССЫПИ редких пятен на мелком шуме (снег тает к пустыне, песок — к снегам):
  редкие проценты на грубом шуме выпадают кластерами в случайных местах, поэтому
  россыпь обязана жить на мелком шуме. Вода — по влажности, редеет в поясах
  (на юге редкие пруды = оазисы). Дальше обычный стек: эрозия земляных пятен и
  зазоры 2 между разными тайлсетами.
- **`rankNormalize(value)`** — ранговая нормализация (значение → доля среди всех,
  0..1 равномерно): порог `rank ≥ 1 − P(ячейка)` держит ЛОКАЛЬНУЮ частоту P.
  **`fbmField(w, h, rng, baseCells)`** — общая с `generateMap` fBm-поля.
- **`generateWorldObjects({ w, h, seed, masks, climate, items, tuning, noManMade })`** →
  `{ placements, pois }`;
  items — реестр (`{name, group, weight, cellsX, cellsY, pass?}`, порядок = индексы реестра).
  `tuning` (0..1, всё необязательно) — ручки густоты растительности: `coreDen`/`edgeDen` —
  плотность посадки в чаще/на опушке (дефолты 0.30/0.07; полог сажается на 20%/17% от
  них), `edgeT`/`coreT` — пороги лесного шума «где начинается опушка/чаща» (0.42/0.62,
  coreT прижимается вверх до edgeT+0.05). `noManMade` (дефолт **true**) — дикий мир:
  деревни не ставятся, из палитр амбиента выбрасываются следы активной человеческой
  деятельности (вывески, колодцы, бочки, мебель, топиары — префиксы
  `sign|banner|well|table_|easel|chalice|lamp_|pot_|topiary|birdhouse|barrel|crate|planter|fence|anvil|stall|notice|loom|spinning`);
  руины, костища и разбитые амфоры остаются.
  1) **POI** (кол-во от площади: деревни ~1/26 000, руины ~1/34 000, костища
     ~1/52 000 клеток): сайты с минимальной чебышёв-дистанцией (gap 24–34),
     деревни любят траву и середину карты, костища — пустыню. Кластер вокруг
     центра: деревня — колодец (север `well_bucket_snow`, юг/середина — колодцы,
     фонтан) + кольцо поддержки (север — снежные вывески/сугробы/бочки; юг/
     середина — заборы/навесы/указатели) + 1–2 ремесленных (кузница, станки);
     руины — врата/кромлех/башня + колонны/обломки; костище — `skull_cow`/
     `skeleton`/`bones_pile` + черепа/ямы/каирны. Вокруг POI — расчистка без
     амбиента. Палитры имён — `WORLD_OBJ_NAMES` (нет в реестре — пропускается).
  2) **Амбиент — растительные сообщества («лесные массивы», `WORLD_VEG`)**. В природе
     деревья одного вида растут патчами (ограничение разлёта семян), массив имеет
     доминанта и спутников, градиент плотности и поляны. Поля: `forest` (чаща F>0.62 /
     опушка 0.42–0.62 / луг), `stand` (шум mid-freq, квантуется в тип сообщества),
     `glade` (поляны в чаще), берега — ивы и камыш в 2 клетках от воды. Стенды по
     климатической фазе клетки: умеренная зона — дубрава / берёзовая роща / смешанный
     лес / хвойный лес; тайга (снежный пояс) — ельники / берёзняки-пионеры / сухостой;
     сухой пояс — ксерофиты / пальмовая роща / колючий скраб. У каждого стенда свой
     подлесок (у дубрав — дубовый лист и грибы, у хвойных — шишки, мхи, хвойный
     росток). Посадка ДВУХПРОХОДНАЯ: сначала полог крупных деревьев стенда (canopy,
     иначе дуб 8×8…10×11 клеток проигрывает footprint-конкуренцию мелким берёзам —
     было 3 дуба на карту, стало ~100), затем подрост/подлесок/кусты. Луг — травы и
     цветы, редкое одиночное дерево (`tree_oak_meadow` «Дуб на поляне»). Садовые и
     парковые растения (горшки, клумбы, топиар, сакура, бонсай) в дикой природе не
     встречаются. Снежный биом — группа snow, но только ВГЛУБЬ снега: снежные
     спрайты нарисованы под снежные тайлы и с кромкой не смотрятся, поэтому весь
     footprint объекта обязан лежать в эрозированной на 1 клетку маске снега
     (зазор ≥1 от края); холодные бесснежные клетки засеваются тайгой
     (ельники/берёзняки `vegZoneStands`), пустынный амбиент на жаркие бесснежные
     клетки остался как был.
     Вода, занятые клетки и расчистки POI пропускаются. Отдельный проход 3 —
     ВОДНЫЕ ОБЪЕКТЫ (группа `water`): ~2% водных клеток получают кувшинку/ряску/
     затопленную корягу; весь footprint обязан лежать на водных тайлах (спрайт —
     декаль со своей водяной основой); у `place` флаг `onWater` снимает запрет
     воды для опорных клеток.
     Посадка амбиента МЯГКАЯ: занятыми считаются только ОПОРНЫЕ клетки типа
     (клетки pass-сетки — ствол/основание; без pass — нижняя строка), поэтому кроны
     соседних деревьев свободно перекрываются и сплетаются в настоящую чащу —
     y-сортировка рисует ствол переднего дерева на фоне кроны заднего (жёсткая
     посадка всем footprint осталась у POI — постройки не врезаются друг в друга).
     ~83% объектов стоят в перекрытии с соседями. Луг сеется комками (клумбоватый
     шум: куртины трав/цветов 10% плотности, между ними голая земля 0.8%);
     универсальные кусты — почти только на опушке, в чаще подлесок своего стенда.
     Проверено: в блоках 10×10 клеток с ≥5 деревьями доминант (≥60%) в 99%.
- **Редактор:** кнопка «🌍 Сгенерировать мир» (размер из полей, сид из поля сида)
  применяет маски к слоям по именам тайлсетов и раскладку к объектам; результат —
  обычная карта: 💾 «Карта (JSON)» сохраняет всё, манифест мир НЕ воспроизводит
  (частоты там глобальные). `state.world.pois` — POI последней генерации;
  API: `__MAPEDITOR.generateWorld({ seed, w, h })` (fire-and-forget, статус в
  строке состояния), `applyView` для выставления вида из кода. Ползунки в шапке
  справа от «сетка данных» — ручки `tuning` (чаща/опушка %, пороги опушки/чащи,
  применяются «🌍 Сгенерировать мир»; порог чащи не опускается ниже опушки+0.05).
  Галочка «без объектов» (дефолт включена) — ручка `noManMade`: дикий мир без
  деревень и следов активной человеческой деятельности.
- Проверено (500×500): пояса монотонны на сидах 7/42/123 (снег 51–72% на севере →
  ≤0.3% на юге; песок зеркально), 22 POI, ~21 000 объектов (~83% в перекрытиях
  крон — чаща), 95% снежных объектов на севере, 100% костей на юге; self-test
  1 021 203/1 021 203 спрайтов; undo/redo на полном снимке 500×500 работает.
  Нижний предел зума снижен до 2% — иначе «⤢ вписать» не мог вписать 500×500
  (16000px мира в ~1000px окна).
  Внимание для Node-тестов: порядок items брать из `objects_data.js` (эталонный
  реестр движка/редактора), а не из `objects.json` — с индекса 405 порядки
  расходятся, от этого зависят индексы палитр и сид раскладки.

### Слой объектов (version 2, modules/dualgrid.js + images/objects/)

Декор поверх пола: 633 объекта с девяти листов арта elven_wood (деревья, кусты,
цветы, камни, постройки, мебель, геммы, руины, рытвины/скелеты, снежные объекты —
группа «snow», категория «Снег», водные объекты — группа «water», категория «Вода»
(41 шт: затопленные коряги и брёвна, ряска, кувшинки, водные камни, кораллы, камыш
на воде — лист 9, декали со своей водяной основой). Пайплайн —
APPEND-ONLY: существующие PNG и записи реестра никогда не пересоздаются
(ручные правки спрайтов не затираются), новые листы дописывает скрипт вида
`scripts/cut_sheet7.py` (сегментация компонент; ключинг белого фона с плавной
альфой и флудом от краёв; «еда белёсой кромки» волной; отсечение полуобрезанных
чужих обрывков у кромки; дедупликация повторов по сигнатуре; отбраковка объектов,
задевающих край исходного листа — визуально целые исключения в `EDGE_OK`;
слипшиеся объекты режутся по шву/сплит-прямоугольником по маске своего компонента).
Первые шесть листов вырезаны удалённым `scripts/cut_objects.py` (логика перенесена,
см. git-историю). Остатки фона за ключингом чистит `images/clean_halo.py`.
Лист 8 (кремовый фон) резал `scripts/cut_sheet8.py`: флуд по цветовой дистанции
от медианы кромки, un-blend от цвета фона, разрезка слипшихся через тени рисунков
по тёмным контурам с эрозией мостиков (тени прилипают к ближайшему контуру),
имена частей — `scripts/cut_sheet8_names.json`.

- **Каждый объект** — отдельная PNG-текстура с размером, кратным тайлу (32×32 …
  288×320). Якорь «нижний центр»: объект «стоит» в ячейке (x, y) основанием по её
  нижней грани, `footprint` занимает `cellsX×cellsY` ячеек (ячейка якоря — низ-центр,
  при чётной ширине объект нависает на клетку влево). Рендер — спрайты с
  `sortableChildren` и `zIndex = (y+1)·ts`: нижние по карте рисуются поверх верхних.
- **Генерация** `generateObjects({ w, h, seed, density, items, avoid }) → [[t,x,y]…]`:
  `density` — процент ячеек, получающих объект; `weight` каждого объекта —
  относительный шанс при выборе (0 — никогда); `avoid` — маска-запрет (в редакторе и
  `mapFromManifest` это «фичи» слоёв с `hideBackground`, т.е. вода). На ячейку ровно
  два вызова RNG → поток стабилен: смена весов не двигает раскладку (меняется только
  выбор объектов), смена плотности — только порог. Footprint объектов при генерации
  не пересекается и должен помещаться в карту. Сид потока: `` `${seed}:objects` ``.
- **API**: `buildObjects({items, ts, w, h})` → контейнер (`objectsMeta`); `syncObjects`
  (полная пересборка), `placeObject`/`eraseObjectAt`/`objectAt` (инкрементально,
  «ластик» берёт верхний объект, чей footprint накрывает ячейку).
- **Файлы v2**: манифест несёт `objects: {density, avoidHideBg, items:[{name, weight}]}`
  (раскладку движок генерирует сам, `mapFromManifest` строит слой объектов над полем);
  файл карты — `objects: {items:[{name, weight}], placements:[[t,x,y]…]}` (готовая
  раскладка, `mapFromJSON` отрисовывает без генерации). `version: 2`, файлы v1
  (без `objects`) читаются как раньше. Имена объектов — имена файлов без расширения;
  текстуры ищутся через тот же справочник `textures`/встроенный `png`, что и тайлсеты.
- **Реестр редактора**: `images/objects/objects_data.js` (подключён `<script>`-тегом,
  как и модуль — работает на `file://`): тот же список + data-URL WebP-lossless
  (P-квантизация PNG портит полупрозрачность tRNS, поэтому WebP). Для игр на http
  текстуры грузятся обычными путями из `images/objects/`. Редактор читает ТОЛЬКО
  data-URL: после ручных правок PNG пересоберите реестр —
  `python images/rebuild_registry.py` (перекодирует PNG в data-URL, метаданные
  сохраняет; `--check` — только отчёт о различиях; записи, чей PNG удалён
  с диска, вычёркиваются по умолчанию, `--noprune` оставляет их со старым
  data-URL — тогда в движке на http текстура по пути окажется битой).
- **Чистка фона**: кеинг листов оставляет по контуру мат (полупрозрачная
  светло-серая каёмка вокруг чёрной обводки) и кремовые карманы фона в
  промежутках между частями объекта. Чистит `python images/clean_halo.py`
  (`--apply` — записать PNG и пересобрать реестр; без него — только отчёт):
  волновое удаление от прозрачного края — нейтральная светлая полупрозрачность
  и почти-цвет-фона непрозрачные пикселы; тёмная полупрозрачность (тень) и
  насыщенное свечение не трогаются, дизайн за обводкой недостижим.
- **Проходимость (для коллизий персонажей)**: у каждого объекта сетка клеток
  cellsX×cellsY (32px), где 1 — непроходимо; по умолчанию непроходима нижняя строка
  (корни/ствол/основание), объект 1×1 непроходим целиком. В редакторе — сетка кликов
  во вкладке «Объекты» ниже инструментов и галка «на карте» (красный оверлей по всем
  расстановкам). Сетка хранится в файлах v2 (`items[i].pass` — строка "0101…",
  построчно сверху вниз) и едет вместе с картой. Для игр:
  `dual.buildCollisionMap({w, h, items, placements, ts})` →
  `{ w, h, blocked: Uint8Array, isBlocked(px, py) }` — `mapFromManifest/mapFromJSON`
  возвращают готовую `result.collision`. Кнопки «💾 все сетки» / «📂 сетки»
  экспортируют/применяют все сетки одним JSON-файлом (для ручной правки); файл,
  положенный как `images/objects/pass_defaults.json`, скрипт вырезки применяет
  к новым объектам поверх авторасчёта, а уже добавленные объекты хранят свои
  сетки в реестре как есть (append-only). Рытьё в земле («рытвины») по умолчанию
  непроходимо целиком.
- **Категории и «реальные размеры»**: у каждого объекта есть категория (`group`) —
  вкладка «Объекты» показывает кнопки-фильтры (Деревья / Растения / Вода / Камни /
  Рытвины / Руины / Строения / Мебель / Предметы / Магия / Снег), палитра фильтруется
  и сортируется по категории. Мелкие по смыслу объекты уменьшены до реальных размеров (ключи/свиток/
  книга — 32×32, а не габарит бочки) — настройка `SHRINK` скрипта вырезки
  (исторически в удалённом `cut_objects.py`; листу 7 не требовалась).

### Редактор карт (dualgrid_editor.html)

Полноценный редактор поверх модуля: те же слои, что и в рантайме (низ → верх),
каждый — свой тайлсет/частота/разброс/outside/hideBackground.

- **Инструменты:** ✏ кисть (размер 1×1…3×3) и 🧽 ластик красят **ячейки данных**;
  🏆 заливка (flood 4-связность); ⬚ выделение рамкой; 🏷 **штамп** — выбираешь тайл из
  палитры 4×4 активного тайлсета и кликом ставишь его (выставляются 4 ячейки под его
  углами; превью следует за курсором). Рисование ведётся по ячейкам данных, тайлы на
  границах пересчитываются автоматически (сущность Dual Grid).
- **Выделение (кусок карты, все слои):** Ctrl+C копия, Ctrl+X вырезать, Del стереть,
  Ctrl+V → клик = место вставки (с превью), Esc отмена.
- **Слои:** 👁 видимость, +/🗑/↑/↓; параметры активного слоя: частота/разброс/зазор
  слайдерами (применяются «🎲 Сгенерировать»), «скрывать фон», «вне карты» 0/1,
  залить/очистить/инверт. Зазор — минимум клеток травы до нижних слоёв с другим
  тайлсетом; нарушения (нарисовали воду вплотную к земле) подсвечиваются красным
  прямо в сетке данных (привязанный слой `on` из проверки исключён). Тайлсет,
  добавленный «📂 Тайлсеты…» поверх существующих
  слоёв, по умолчанию наслаивается («скрывать фон» включён) — иначе его

- **Генерация и файлы:** 🎲 генерирует ВСЕ слои по текущим параметрам (тот же код

## Производительность (стенд: вкладка 143 Гц, мир 1600×1200, юниты с коллизиями и HP)

Замеры стресс-теста (полигон game.js, популяция наращивается через `window.__TEST.spawnWanderer`):

| Сущностей | До culling | Culling | + парные ячейки 32px + WebGPU | + точная ячейка 16px (итог) |
|---|---|---|---|---|
| 15 061 | 62 FPS / 17.4 мс | ~70 FPS / ~15 мс | 85 FPS / 12.6 мс* | ~100 FPS / 10.0 мс |
| 25 061 | 32.5 FPS / 31.4 мс | ~40 FPS | 43 FPS / 24.3 мс* | ~59 FPS / 16.9 мс |

\* на объектах до уполовнивания; после — 21.16 мс на 25k (та же конфигурация, свежий замер).

Порог «без лагов» (≥60 FPS): **~23 тыс.** объектов (21k → 67.7 FPS / 15.8 мс, 24k → 56.4 FPS / 18.4 мс).

Разложение выигрыша на 25 061 сущности (A/B, мс кадра): старая коллизия + WebGL — 31.44;
**парные ячейки + WebGL — 25.44 (−19% от алгоритма)**; парные ячейки + **WebGPU — 24.31
(−4% от рендерера)**. Вкладка теста поддерживает WebGPU — он реально активен
(`app.renderer.name === "webgpu"`); в браузерах без WebGPU движок сам откатывается на WebGL.

**Главный вывод:** после culling-а узкое место — не отрисовка и не плотность коллизий
(расширение мира вчетверо почти не помогало), а **линейные расходы на каждую сущность**:
движение, перестройка сетки, скан соседей коллизий, сам цикл рендера и обход сцены Pixi
(~0.6–0.7 мкс/сущность суммарно). Дальнейшие резервы (по убыванию эффекта):
LOD-пропускание физики для далёких/спящих групп, обход коллизий по парам ячеек вместо
скана 3×3 на каждую сущность, вынос физики в Web Worker (SharedArrayBuffer), WebGPU-рендерер.

**Culling в ядре (как работает):** `renderSystem` вычисляет вид-прямоугольник из трансформа
контейнера мира (`scale`, `pivot` + запас `CULL_MARGIN = 32`) и ставит спрайтам `visible`.
Без модуля камеры прямоугольник совпадает с экраном — поведение корректно само по себе.
`animationSystem` пропускает скрытых (видимость прошлого кадра, лаг 1 кадр перекрывается
запасом). Проверено: флаг видимости точно совпадает с прямоугольником вида на 23.5k.

## Редактор персонажей (editor.html)

Пиксельный редактор: сетка 64×64 по умолчанию (**размер холста меняется 8..256**,
шаг 8, содержимое переносится с центровкой; зум подстраивается автоматически),
палитра + свой цвет, инструменты (пиксель / заливка / ластик / пипетка),
**строки-анимации** (именованные ряды: wait, death, …), кадры внутри строки,
проигрывание, экспорт сеткой: **строка = анимация, колонка = кадр**. Строки
выравниваются по максимальной длине (недостающие кадры — повтор последнего).
Результат: `images/sprites/<имя>.png` (сетка) + `<имя>.json` (манифест: size,
columns, **fps**, animations[{name,row,frames}]). Скорость проигрывания
(«кадр/с», поле у кнопки проигрывания) пишется в манифест: редактор играет с
ней, `assets.loadCharacter` отдаёт её как `fps` и `animationSpeed` (fps/60) —
достаточно `sprite.animationSpeed = char.animationSpeed`. Внизу редактора —
превью всего спрайтшита (клик по кадру — перейти к нему).
Два способа сохранения: **«Сохранить на сервер»** (POST /save — нужен сервер
разработки) и **«Скачать (download)»** (браузер скачивает PNG+JSON напрямую —
работает везде, включая file://).

**Открытие**: кнопка «Открыть» вызывает системный диалог выбора файла —
выберите .png и рядом его .json (файлы читаются локально, сервер не нужен).
Если .json не выбран, редактор пробует взять его из images/sprites/. Разбор
проверен round-trip: открыть → экспорт → открыть — пиксели совпадают.
Манифест обязателен: PNG без него не открывается.

Загрузка в игре — один вызов хелпера модуля assets (кэширует и PNG, и манифест):

```js
const mage = await assets.loadCharacter("images/sprites/mage_64.png");
// mage.animations.wait / mage.animations.death — массивы текстур AnimatedSprite;
// переключение анимации: sprite.textures = mage.animations.death; sprite.gotoAndPlay(0);
// для проигрывания один раз: sprite.loop = false (смерть застывает на последнем кадре)
```

(формат манифеста: `{size, columns, animations:[{name,row,frames}]}` — при желании
доступен напрямую через `assets.get("<путь>#manifest")`).

**Готовые персонажи** (`images/sprites/` + код рисования в `scripts/drawings/`):
mage_64 (wait+death), elf_64 (4 walk), warrior_128, necromancer_128 и
barbarian_128 — стандартный набор (4 walk + 4 attack + wait + death + damage,
43 кадра). Рисователи с 128px используют кривые/эллипсы, автообводку силуэта,
наземную тень и форменные тени (свет сверху-слева); сборка кадров идемпотентна.
Правила слоёв эффектов: `flipX()` — последняя операция кадра (эффект отражается
вместе с персонажем); удар «по ту сторону» фигуры (вид сзади) рисуется ДО тела
(хук `behind`) — перекрывается силуэтом, поверх (`front`) только то, что в
воздухе. LN принимает только целые координаты (float → бесконечный цикл
Брезенхэма; в drawings LN округляет вход и имеет guard).

**priest_128** — персонаж, сгенерированный ИИ-пайплайном (SD-модель Retro Diffusion +
IPAdapter Plus + ControlNet openpose/depth; скелеты поз и карты глубины рендерятся
программно; пайплайн вне репозитория — D:\ZCode\ComfyUI). Стандарт 5×11, 43 кадра,
fps 8. Вид «сзади» генерится из отдельной back-базы (img2img d0.5, без лица),
«смерть»: ИИ даёт отшат/оседание, финальная «груда» — программное сплющивание
последнего кадра + затемнение. Лежачие позы модель не умеет — при замене на
процедурный рисовальщик учесть.

API автоматизации — `window.__EDITOR` (консоль/агент):

```js

E.mirror();                 // левая половина → правая
```

## Известные ограничения и идеи на будущее

- **32 компонента максимум** (битовая маска Uint32). При исчерпании — две половины Uint32 или
  таблица соответствий.
- `ECS.nextId` — глобальный, а не на world: несколько миров будут конфликтовать по ID.
- При экстремальной плотности (в разы выше «ёмкости» мира по кругам) коллизии расталкивают
  юниты за границы мира — толчение позиций в collisionSystem не ограничено стенками.
  Для игровых плотностей не проявляется.
- Скорости столкновений (импульс отскока) остаются в «пикселях за кадр» — при смене dt-масштаба
  скоростей проверить collisionSystem.
- Анимации AnimatedSprite уже кадронезависимы (сам спрайт читает deltaTime тикера).
- Звук — синтез, файлы не подключены.
